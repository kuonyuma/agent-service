# CLI Agent 产品需求与学习路线

## 文档定位

- **甲方目标**：将现有 Agent 半成品完善为可以长期使用、可控、可恢复、可验证、可衡量的本地 CLI 编程助手。
- **乙方目标**：通过逐项实现真实需求，学习持久化、异步与进程管理、安全、状态机、并发控制、容错和工程评测。
- **需求范围**：CLI 及其背后的 Runtime、工具和子代理，不涉及 Web 页面、HTTP API 或 Web 数据库链路。
- **交付方式**：本文是分期交付的需求池，不要求一次完成全部模块；第四期为进阶选修。
- **状态说明**：需求与验收标准描述的是目标能力，不代表已经实现。现状表已按五模块内核重构更新；架构回归不等于本文全部产品需求已验收，真实模型能力仍需单独验证。
- **接口说明**：文中的斜杠命令是拟议交互，不代表当前 CLI 已支持；具体命名可在设计时确定。
- **路径说明**：下文源码路径均相对于仓库根目录，以模块和符号定位，避免重构后行号失效。

核心原则：

> 不是继续堆积 Agent 角色和工具，而是把“能跑通的 Agent”做成“可以放心长期使用、出错能够解释、修改能够验证、任务能够恢复的 CLI 产品”。

## 一、产品目标与典型场景

甲方需要一个在本地代码仓库里工作的 CLI 编程助手。

典型使用流程：

1. 进入陌生项目，让 Agent 解释代码和定位问题。
2. Agent 提出计划，说明准备读取什么、修改什么、执行什么。
3. 用户批准必要操作。
4. Agent 修改代码、执行检查，并交付有证据的结果。
5. 用户查看改动，并在需要时撤销改动。
6. 即使关闭终端、网络断开或任务中断，之后也能继续工作。
7. 用户始终知道 Agent 做了什么、为什么失败、花了多少资源。

## 二、现状与需求依据

当前实现已经具备规划与反思、并发子代理、上下文压缩、权限确认、流式输出、输出安全审核以及单元和集成测试。因此，下文涉及这些领域的要求是升级已有能力，而不是重新实现一遍。

| 当前实现 | 对产品的影响 |
| --- | --- |
| `src/agent_service/adapters/cli/app.py` 的历史保存在 `self.contents` 中 | 关闭进程后，CLI 没有可恢复的持久会话 |
| `src/agent_service/adapters/tools/run_command.py` 使用 `asyncio.to_thread(subprocess.run, ...)` | 仍缺命令超时、实时日志和进程生命周期管理；取消协程不等于终止命令进程 |
| `src/agent_service/adapters/tools/run_command.py` 已将非零退出码标记为工具错误 | 失败不能冒充验证成功，但零退出仍不代表执行了有意义的验证 |
| `src/agent_service/kernel/strategy/policy.py` 按路径记录修改，同批次或子代理验证不能自动核销父级修改 | 验证提醒仍是有限策略，不是测试覆盖或正确性的证明；仍需结构化证据与交付约束 |
| `src/agent_service/kernel/context/compression.py` 按消息条数触发压缩，并注入模型端口 | 下一步是解决预算、信息保留和可追溯性 |

## 三、第一期：可信的日常使用基础

### 需求 01：会话工作台与历史持久化

**甲方场景**

> 昨天分析了一个问题，今天打开终端，希望接着聊，而不是重新解释整个背景。

**功能要求**

- 创建、列出、切换、重命名会话。
- 恢复历史会话。
- 导出可阅读的会话记录。
- 界面始终显示当前会话和工作目录。
- 保存目录可配置。

拟议交互：

```text
/new
/sessions
/resume <会话ID>
/rename <名称>
/export <文件路径>
```

**验收标准**

1. 完成两轮对话，退出程序，重新启动后能恢复。
2. 会话 A 的内容不能混入会话 B。
3. 包含工具调用的历史能够正确恢复，不能出现只有工具响应、没有对应调用的残缺上下文。
4. 保存中断或文件损坏时，要给出明确提示，不能直接覆盖原数据。
5. 恢复历史不能自动重新执行历史命令。

**学习方向**

序列化、数据模型、存储格式版本、原子写入、数据迁移、交互命令路由。

**范围边界**

本需求恢复“聊过什么”；恢复“运行到哪一步”由需求 08 处理。

### 需求 02：真正可控的命令执行器

**甲方场景**

> 让 Agent 运行测试，测试卡住了。需要看见输出，也需要真正停止它。

**功能要求**

- 指定工作目录、超时时间。
- 实时显示标准输出和错误输出。
- 限制输出量，超出部分明确标记或保存为日志。
- 返回结构化结果：退出码、耗时、是否超时、是否取消。
- 用户取消时，终止这次任务启动的进程及其子进程。

**验收标准**

1. 一个每秒输出一行的测试程序，输出应逐行出现，而不是结束后一起出现。
2. 超时命令能被终止，并返回“超时”，不能伪装成正常完成。
3. 用测试用父子进程验证取消行为，不留下后台子进程。
4. 退出码非零必须保留，并能影响后续验证判断。
5. 大量输出不能让终端和内存失控。

**学习方向**

`asyncio` 子进程、并发读取管道、背压、超时与取消、Windows 进程管理。

**关键边界**

取消 Python 的等待任务，与停止操作系统进程是两回事。

### 需求 03：工作区边界与分级权限

**甲方场景**

> 允许 Agent 修当前项目，不代表允许它修改电脑上的任意文件。

**功能要求**

- 明确声明当前工作区。
- 提供只读、允许编辑、允许执行命令等权限模式。
- 审批时展示实际路径、操作内容和风险信息。
- 支持范围明确、可以撤销的授权规则。
- 拒绝访问敏感路径和越界路径。

**验收标准**

1. `../`、绝对路径、符号链接或 Windows reparse point 不能绕过文件访问策略。
2. 只读模式下，模型即使请求写工具，也不能执行。
3. 拒绝审批后，不产生对应副作用。
4. 文件、网页或命令输出里的文字不能授予权限。
5. 子代理的权限不能超过父任务。

**学习方向**

最小权限、路径规范化、策略与执行分离、权限继承、攻击面分析。

**关键边界**

文件工具限制在工作区，不等于任意 Shell 命令也被沙箱隔离。不能用一套路径检查就宣称完成了命令沙箱。

### 需求 04：有证据的验证与交付报告

**甲方场景**

> Agent 说“修好了”，需要知道这是读了一遍代码、通过了静态检查，还是相关测试真的通过了。

**功能要求**

区分以下状态：

- 已修改。
- 已人工式检查／重新读取。
- 静态检查通过。
- 相关测试通过。
- 尚未验证。
- 验证失败。

最终报告必须包含：

- 修改了哪些文件。
- 执行了哪些检查。
- 检查结果和退出码。
- 哪些部分没有验证。
- 已知风险和剩余问题。

**验收标准**

1. 重新读取文件，不能标记为“测试通过”。
2. 测试退出码非零，不能进入“验证成功”状态。
3. 验证后再次修改相关文件，旧验证结果需要失效或标记为过期。
4. 子代理的验证结果也必须附带证据，不能仅凭一句“我测过了”。
5. 没有条件运行测试时，明确说“未验证”。

**学习方向**

状态机、领域建模、结构化工具结果、证据关联、状态不变量。

**交付原则**

Agent 可以失败，但不能把失败包装成成功。

## 四、第二期：更长、更复杂的任务

### 需求 05：变更预览与安全撤销

**甲方场景**

> Agent 准备改五个文件，希望先看改动。改完不满意，也不能把用户之前写的代码一起撤掉。

**功能要求**

- 修改前展示 diff。
- 将一次任务的修改归为一个变更集。
- 记录修改前后的版本信息。
- 支持撤销 Agent 自己的改动。
- 检测外部修改冲突。

**验收标准**

1. Agent 读取文件后，用户手动修改同一文件，Agent 不能直接覆盖用户的新内容。
2. 撤销不能使用粗暴的全仓库重置，不能丢失用户已有修改。
3. 单文件写入中断不能留下半截文件。
4. 多文件修改部分失败时，要明确指出哪些成功、哪些失败，并提供恢复策略。

**学习方向**

乐观并发控制、文件指纹、原子替换、补丁、操作日志、Git 工作区语义。

**与现状的关系**

已有进程内文件锁是基础，但“避免同时写入”不等于“避免覆盖过期内容”。

### 需求 06：面向代码库的检索工具

**甲方场景**

> 仓库里有几千个文件，询问“这个异常从哪里抛出来”，Agent 不应该挨个完整读取文件。

**功能要求**

- 按文件名或 glob 搜索。
- 按文本或正则搜索，返回路径、行号和上下文。
- 分段读取文件。
- 尊重忽略规则，跳过明显的二进制文件。
- 搜索结果可分页、可限制大小。

**验收标准**

1. 在一个预置测试仓库里，能够定位指定异常的定义和调用位置。
2. 大文件可以按行读取，不必整份塞给模型。
3. 超过结果上限时明确告知截断，不能让模型误以为只有这些匹配。
4. 回答中的代码引用能定位到实际文件和行。

**学习方向**

检索接口设计、工具输出预算、文本搜索、文件系统遍历、检索质量评估。

**范围边界**

第一版不要求向量数据库。先把普通代码搜索做好，再考虑语义检索。

### 需求 07：可管理的上下文预算

**甲方场景**

> 聊久了，Agent 不能忘记用户一开始说的“不要改公开接口”，也不能突然因为上下文过长而失败。

**功能要求**

- 查看当前上下文占用及其来源。
- 根据 token 预算，而不只是消息数量，决定压缩。
- 分开管理关键约束、任务状态、普通历史和大块工具输出。
- 保留原始记录，让摘要可以追溯。
- 支持查看和手动触发压缩。

**验收标准**

1. 用固定长对话测试：压缩后仍保留用户约束、未完成事项和关键错误信息。
2. 工具调用与响应保持合法配对。
3. 大量命令日志不会挤掉核心任务要求。
4. 无法在预算内保留必要信息时，明确报错或要求用户缩小任务。
5. token 估算值与实际使用量分开展示，不能混为一谈。

**学习方向**

上下文窗口、token 计量、分层记忆、摘要策略、信息丢失评估。

### 需求 08：任务中断、故障恢复与受控重试

**甲方场景**

> 网络断了、模型限流了、程序崩了，不应丢掉全部进展，更不希望恢复时把有副作用的操作执行两次。

**功能要求**

- 明确记录运行、等待审批、取消、失败、中断、完成等状态。
- 保存任务检查点。
- 临时网络错误采用有上限的重试。
- 重启后展示中断任务，让用户决定如何继续。
- 对“是否已经执行成功不确定”的操作，单独处理。

**验收标准**

1. 在模型响应、等待审批、工具执行等位置注入故障，都能得到合理终态。
2. 重启后，旧审批不能直接变成新授权。
3. 如果命令可能已经执行，但结果没有保存，必须标记“结果未知”，不能盲目重跑。
4. 重试受次数、时间和预算限制。
5. 保留当前单次运行的 10 轮上限，不能靠无限循环实现“坚持到完成”。

**学习方向**

持久化状态机、检查点、幂等性、指数退避、故障注入、取消传播。

## 五、第三期：可维护、可自动化、可衡量

### 需求 09：运行追踪与资源预算

**甲方场景**

> 一次任务很慢、很贵，需要知道时间和 token 花在哪里。

**功能要求**

- 查看主任务、子代理、工具的执行时间线。
- 每次运行拥有可追踪的 ID。
- 统计主模型、子代理、安全审核和上下文压缩的消耗。
- 设置 token、耗时、工具调用次数等预算。
- 导出经过脱敏的诊断信息。

**验收标准**

1. 能从最终失败定位到具体工具调用和错误。
2. 子代理消耗计入父任务总账。
3. 缺少 usage 数据时显示“未知”，不能当作零。
4. 达到预算后不再启动新的工作，并明确解释原因。
5. 日志不直接泄漏 API key 等凭据。

**学习方向**

事件模型、可观测性、追踪关联、资源配额、日志脱敏。

### 需求 10：项目配置与可控的项目记忆

**甲方场景**

> 不同项目有不同的测试命令和编码约定。不想每次重新告诉 Agent，但也不希望它偷偷记住不该记的东西。

**功能要求**

- 项目级配置：模型、预算、工作区、权限模式等。
- 明确配置优先级。
- 读取经用户确认的项目约定文件。
- 记忆可以查看、修改、删除，并显示来源。
- 提供诊断命令，检查配置与依赖问题。

**验收标准**

1. 能解释某个配置最终来自启动参数、环境变量还是项目配置。
2. 切换项目时不会串用另一个项目的规则。
3. 项目规则不能扩大执行权限。
4. 普通诊断不会触发付费模型请求；需要联网测试时另外确认。
5. 不自动把密钥和临时工具输出写入长期记忆。

**学习方向**

配置分层、作用域、可信边界、知识来源管理、隐私控制。

### 需求 11：非交互模式与脚本集成

**甲方场景**

> 希望在 PowerShell 脚本或 CI 中调用 Agent，而不只能坐在终端前聊天。

**功能要求**

- 从参数、文件或标准输入接收任务。
- 输出适合机器消费的 JSON／JSONL。
- 提供明确的退出码。
- 非交互模式遇到审批需求时，按策略拒绝或退出，不能一直等输入。
- 日志与结构化输出分离。

**验收标准**

1. 标准输出中的 JSON 可以直接解析，不混入终端颜色码或提示文案。
2. 成功、任务失败、需要审批、用户取消能够区分。
3. 无交互环境下不会卡在 `y/n` 提示。
4. 默认不能因为“无人值守”就跳过权限检查。

**学习方向**

CLI 协议设计、流式结构化输出、退出码约定、管道与自动化测试。

### 需求 12：升级现有多代理协作

**甲方场景**

> 两个子代理一起工作，应该更高效，而不是互相覆盖文件、重复探索、一起消耗预算。

**功能要求**

- 将已有依赖交接发展为明确的任务依赖关系。
- 展示每个子任务的状态、输入、产物和失败原因。
- 对冲突修改制定策略：串行、独立工作区或拒绝。
- 子代理共享总预算。
- 父任务取消时，统一清理子任务。

**验收标准**

1. A 失败时，依赖 A 的 B 不能拿着不存在的结果继续运行。
2. 两个 worker 修改同一文件时，不能悄悄互相覆盖。
3. 父任务结束后，不遗留无主后台工作。
4. 同一组任务对比单代理和多代理，报告成功率、耗时和 token，而不是只展示“同时跑了几个”。

**学习方向**

依赖图、调度、结构化并发、资源竞争、结果汇聚、性能实验设计。

**与现状的关系**

现有实现已经支持子代理。本需求不是增加几个角色，而是提高协作可靠性和可衡量的收益。

### 需求 13：Agent 任务级评测系统

**甲方场景**

> 新版本是否更聪明、更稳定，需要数据，而不是一次演示。

**功能要求**

- 建立至少 10 个小型、可重复的代码任务。
- 覆盖代码定位、修改、测试失败、审批拒绝、工具超时等情况。
- 支持离线模拟模型响应，验证运行流程。
- 可选运行真实模型评测。
- 记录模型、配置、提示词版本。

**验收标准**

1. 成功与否由文件结果、测试和执行记录判定，不能只听模型自评。
2. 输出任务成功率、错误宣称完成的比例、耗时和 token。
3. 能比较两版实现的变化。
4. 事件回放默认只重现过程，不重新执行历史命令。
5. 故障测试使用隔离目录，不碰真实用户数据。

**学习方向**

评测集设计、确定性测试与概率性评测的区别、回归分析、实验控制。

**实施要求**

这不是替代已有单元与集成测试，而是验证整个 Agent 完成任务的能力。不要等到第三期结束才开始，可以从第一期就积累测试任务。

## 六、第四期：进阶选修模块

以下模块不是第一阶段的前置条件，可按兴趣和实际需要选择。

| 模块 | 甲方需求 | 主要学习方向 |
| --- | --- | --- |
| MCP／插件工具接入 | 不修改核心循环就能接入外部工具；仍受审批、超时和预算约束 | 协议适配、Schema 校验、插件生命周期、故障隔离 |
| 多模型后端 | 可以切换模型服务，统一流式事件、工具调用和 usage；切换不能导致副作用重放 | 适配器、接口抽象、兼容性测试、降级策略 |
| 本地知识库 | 对文档和历史决策进行检索，答案带来源；文件变化后索引可更新 | 切块、混合检索、索引失效、检索评测 |
| 独立工作区开发 | 在 Git worktree 中执行修改，验证后再由用户决定合并 | Git、隔离环境、冲突处理、交付边界 |
| 可复用任务模板 | 把“检查项目”“修复测试”“生成变更说明”等流程参数化 | 工作流建模、输入校验、步骤依赖、版本管理 |

验收看实际解决了什么问题，不以是否使用向量数据库、多个模型或更多 Agent 作为先进程度的依据。

## 七、首个交付任务：会话持久化 MVP

### 7.1 本次范围

先只做四件事：

1. `/new`：创建会话。
2. `/sessions`：列出会话。
3. `/resume <id>`：恢复会话。
4. 每轮结束后保存历史。

### 7.2 暂不包含

- 正在执行中的任务恢复。
- 多代理断点续跑。
- 向量数据库。
- 更换 Agent 框架。
- 跨设备同步。

### 7.3 验收步骤

1. 新建会话 A，完成一轮普通问答和一轮只读工具调用。
2. 新建会话 B，输入不同的内容。
3. 退出程序并重新启动。
4. 分别恢复 A、B，确认历史正确且彼此隔离。
5. 恢复时没有重新执行任何历史工具。
6. 人为损坏一份测试会话文件，程序能报告问题，其他会话仍然可用。
7. 相关测试不依赖真实 Gemini API。

### 7.4 交付物

- 功能代码。
- 自动化测试。
- 一页简短设计说明：数据保存在哪里、格式是什么、何时保存、写入失败怎么办。
- 已知限制。

### 7.5 技术方案与取舍

技术方案由乙方决定，但需要解释取舍。选择 JSON、JSONL 或 SQLite 都可以，重点是为什么适合当前需求，而不是使用名称更复杂的技术。

## 八、推荐推进顺序

**会话持久化 → 命令生命周期 → 权限边界 → 验证证据 → 安全变更 → 上下文与恢复 → 自动化与评测。**

代码检索可在第二期并行规划，评测任务从第一期开始积累；其余模块按实际依赖和兴趣安排。

每个需求都应通过具体场景、可执行的验收标准和明确的交付物来推进，让学习围绕真实问题展开，而不是单纯继续添加工具。
